# crates/ss-magic – the sync CLI

Binary `ss-magic` (tag `vX.Y.Z`): the interactive sync CLI. Repository-wide rules live in the root [CLAUDE.md](../../CLAUDE.md).

Code rules: the root [CODING_STANDARDS.md](../../CODING_STANDARDS.md), plus [src/orca/CODING_STANDARDS.md](./src/orca/CODING_STANDARDS.md) for Orca code.

## Crate layout

The crate depends on `ss-magic-core` and NEVER on the plugin crate. It owns the updater (`self_update`) and the prompt/TUI libraries (`inquire`, `ratatui`); `saphyr` is its dependency alone (see below).

`crates/ss-magic/src/`:

- `main.rs`, `cli.rs`, `pack.rs` (the engine; re-exports `repo_name_stem` from core's `reponame.rs`)
- `sync/{mod, reverse_sync, merge}.rs` – the interactive half of sync; `sync/mod.rs` re-exports core's `apply` / `pattern` / `repo_scan` / `under_excluded_tree`
- `tui/` – `inquire` wrappers, theme, menu, cockpit, diff model; `tui/mod.rs` re-exports core's `style`
- `workspace/{mod, migrate}.rs` – `workspace/mod.rs` re-exports core's `superset_files`
- `orca/{mod, detect, orca_yaml, shared_dirs, snapshot, worktreeinclude, write}.rs` – Orca compatibility
- `update/{mod, apply}.rs`
- crate-root tests under `tests/` (`sync.rs`, `reverse_sync_flow.rs`, `update_gate.rs`, `orca_flow.rs`)

`main.rs` re-exports core's `git` and `hashing` under `crate::git` / `crate::hashing`, so paths inside the CLI read `crate::git::…`.

## Modules

- `cli.rs` – hand-rolled arg parser (no `clap`), pure and unit-testable without spawning the process.
  - `parse(&[String]) -> Parsed` selects `Command::{Bare, Sync { no_backup, no_orca_skip }, ReverseSync { no_backup }, Pack, Orca, Update}` from the first non-flag arg (absent → `Bare`; `sync` → forward copy; `reverse-sync` → reverse copy; `orca` → the explicit Orca refresh). `init [PATTERN...]` parses to `Parsed::Init(patterns)`, carried apart from `Command`. An unknown subcommand is `Parsed::Error(token)`. `Command` stays `Copy`/`Eq`.
  - `--help`/`-h` short-circuits to `Parsed::Help`. `orca` is the ONE subcommand after which `-h`/`--help` still yields `Parsed::Help`: it rewrites files in the shared main checkout, and "what does this do?" must not be answered by doing it.
  - `has_no_backup` is a whole-slice scan for `--no-backup`/`-n` anywhere in argv (before OR after the subcommand token – deliberately asymmetric with the terminal `-h`/`--help` short-circuit). `has_no_orca_skip` scans the same way for `--no-orca-skip` (long form only): it makes forward sync in an Orca worktree copy the `.worktreeinclude` paths too instead of leaving them to Orca.
  - There is NO `plugin` token and no `Parsed::Plugin`: the retired `ss-magic` + `plugin` subcommand form takes the ordinary `Parsed::Error` path, with no alias or redirect.
  - `--version`/`-V` short-circuits to `Parsed::Version` and wins over everything. `version_requested` scans PAST a subcommand token, so `ss-magic sync --version` prints the version instead of falling through to the update-gated `Bare` menu when a script shells out to identify the binary. Do not reintroduce a plugin token or a scan stop.
- `main.rs` – composes everything: `cli::parse` → `tui::style::init`, then `tui::theme::install` → [auto-update gate for `Bare`/`Sync`/`ReverseSync`/`Pack`/`Orca`, per `should_run_update_gate`] → `dispatch`.
  - `should_run_update_gate` is an INCLUSION list over `Command`. `Parsed::Version` prints `version_line()` and stops before any dispatch.
  - `Bare` routes to `tui::menu::run`.
  - `Sync { no_backup, no_orca_skip }` runs the non-interactive forward copy: `run_sync_flow` → `sync_core(cwd, SyncOptions, env, on_event)`. It runs the pre-copy backup pass (`reverse_sync::backup_forward_targets`) before `sync::apply::run_filtered`, unless `--no-backup`. `resolve_sync_roots` resolves the cwd + main-checkout roots shared by the forward and reverse flows; `print_event` renders the `sync::apply::Event` stream.
  - `env` is how the Orca variables are read: production passes the process environment, tests pass a closure, so no test depends on the terminal it was launched from (which may itself be an Orca terminal).
  - In an Orca worktree (`orca::detect`), and unless `--no-orca-skip` was given, the copy's `PathFilter` is the skip set built by `orca_skip_filter` – read ONCE from the main checkout's `.worktreeinclude`, before anything is copied. A successful copy is then followed by `orca::write::refresh_snapshot`, reported by `report_snapshot_refresh` and never allowed to change the exit status. `sync_summary_line` adds "left N path(s) to Orca" to the result line only when something was left.
  - `Orca` runs `run_orca_flow` → `orca_core`, the explicit refresh: it resolves the main checkout from any directory of the repository, needs `magic.json` there like `pack`, and returns the notices so tests can read them.
  - `ReverseSync { no_backup }` runs `run_reverse_sync_flow`, which hard-errors from the main checkout (nothing to push) and otherwise bulk-pushes via `reverse_sync::run_bulk`.
  - `Pack` runs `pack::pack_core` (`run_pack_flow` + `print_pack_event`). `Update` forces a self-update.
- `workspace/migrate.rs` – detect + migrate/init branching off `config.json`'s `setup` (old `setup.sh` reference → migrate; `magic.sh` marker → normal; neither → init).
  - Stages renames/writes/deletes into a tempdir and materializes via `copy_into_repo` only after the finishing-action prompt. `run_init_noninteractive` is the TUI-free init behind `ss-magic init` (layout from CLI patterns, no prompt, not gated by auto-update).
  - `materialize_init` is the one helper behind everything `run_init` (also the edit-config path) and `run_init_noninteractive` do once decisions are made: stage, `copy_into_repo`, bootstrap gitignores, Orca files. `materialize_migration` is its migrate counterpart, split from `run_migrate` so the whole write is testable without a prompt.
  - **Orca output is computed before the prompt and written after the tree materializes.** `orca::write::plan` runs first so the "This will:" list says whether `orca.yaml` is created, updated or cannot be edited, how many files Orca will copy, and whether `.worktreeinclude` gains an ignore rule, is already gitignored, or is tracked and gets none. `Plan::apply` runs after the tree is written; the plan remembers what it read, and `apply` leaves alone, with a warning, a file that changed on disk in the meantime.
  - `overlaid_patterns` gives the plan the sync patterns as they WILL be (the `files` about to be written plus the local overlay), since `magic.json` is not on disk yet. It returns `(patterns, Option<warning>)` and never fails: an unparseable overlay contributes no patterns and yields a warning each call site prints to stderr (`warn_overlay`). A broken per-machine file must not stop init, edit config or migrate, and leaving its patterns out of Orca's list is safe because forward sync still copies them.
  - The `setup` array both init paths write is `init_setup(existing)`: the existing array with any `setup.sh` reference replaced in place (`migrated_setup`, which only the scripted init can meet, and which DROPS the reference instead when another entry already runs the sync in any spelling `entry_is_magic_marker` accepts, so the sync never runs twice), and the wrapper put FIRST only when no entry is a wrapper or sync marker yet. Every other command stays where it was – writing `[wrapper]` alone would silently delete commands such as `pnpm install` from every Superset workspace created afterwards.
  - The summary's overlay line comes from `local_overlay_line(exists, ignored)`: "Bootstrap" or "Keep" `magic.local.json`, then "+ add it to .gitignore" or "(already gitignored)", since a second run creates no file and adds no rule.
  - Interactive init runs a second picker (`ui::pick_shared_directories`) for `magic.json`'s `sharedDirectories`: what starts checked is the stored list when the key exists (a stored "none" included), otherwise every kind that matches something. With nobody to ask, `shared_dirs::stored_or_detected` keeps a stored list and otherwise stores every default kind that matches, leaving the key absent when none does.
  - `execute_final_action` stages `FINAL_ACTION_PATHS` – `.superset`, `.gitignore` and `orca.yaml`, NEVER the per-machine `.worktreeinclude`.
  - All three write paths (`run_migrate`, `run_init`, `run_init_noninteractive`) call `ensure_bootstrap_gitignores`, which gitignores THREE things, each at the closest existing `.gitignore` (or the git-root file) and git-tolerant (degrading to a literal append in non-git test tempdirs): `magic.local.json` (a `gitignore::ensure_path_ignored` `File` rule); the tool's `.superset/backups/` tree (via `reverse_sync::ensure_backups_ignored`, the same `Dir` rule the first sync would add lazily); and the plugin's `.superset/.magic/` state tree (via core's `state_tree::ensure_state_ignored`, that rule's one owner). Ignoring backups up front means a fresh `ss-magic init` protects the backup tree before any secret bytes are backed up. A fourth rule, for `.worktreeinclude`, is NOT written here: `orca::write::Plan::apply` adds it afterwards, and only when the plan found that file untracked.
- `pack.rs` – `ss-magic pack`: expands the overlaid `magic.json` patterns against the current git repo root (via `sync/apply.rs`'s `match_paths`) and writes the matches, repo-relative, into `ss-magic-<repo>.tar.bz2` at that root. The config source, match target and archive destination are all the one `cwd_repo_root`.
  - `archive_file_name` derives `<repo>` from the normalized `origin` remote (scheme/userinfo/host stripped, segments sanitized and joined with `_` – identical for ssh/https/scp forms; nested GitLab groups keep all segments), falling back to the primary worktree basename, then `files`. `repo_name_stem` is the stem derivation behind it, owned by core's `reponame.rs` (with `stem_from_origin` and `sanitize_segment`) and reused verbatim by the plugin's identity slug, so the two can never disagree about what this repo is called.
  - `pack_core(cwd, on_event)` mirrors `main::sync_core`'s control flow (resolve root → probe magic.json → load overlaid → empty guard → work) and emits a `PackEvent` stream. A successful pack emits `PackEvent::Done { out_path, count }`; `count` is UNIQUE FILE PATHS (the `added: HashSet<PathBuf>` of files and symlinks actually written), not tar entries – directories are not counted and two overlapping patterns naming the same file count once.
  - The rendering layer (`main.rs::print_pack_event`) owns the summary line, the `tar -xjvf` extraction hint, and `copy_to_clipboard` (pbcopy/wl-copy/xclip/xsel) of the archive's canonical path. The clipboard is deliberately outside `pack_core` so tests never touch it.
  - `write_archive` tars into a bzip2 stream (`bzip2` crate, pure-Rust `libbz2-rs-sys` backend – no C toolchain) via a `NamedTempFile` in the root, then persists atomically.
  - Safety:
    - It never packs a pack archive into itself: every root-level `ss-magic-*.tar.bz2` match is excluded (current derived name, legacy fixed name, archives from a previous origin's name), as is a `.` match that resolves to the repo root.
    - It excludes every `sync::EXCLUDED_TREES` tree, so neither a recovered secret under `.superset/backups/` nor the plugin's `.superset/.magic/` state is ever packed. A LEAF match goes through the flat `sync::under_excluded_tree` retain filter; a directory match that is an ANCESTOR of one (a bare `.superset` pattern, or a broad `**`) goes through `append_dir_excluding_trees`, whose recursive `WalkDir` `filter_entry` prunes each excluded subtree the flat filter cannot catch. One directory match can sit above several at once, since `.superset` is the ancestor of BOTH `backups` and `.magic`.
    - It classifies each match with `symlink_metadata` (no-follow), so a matched symlink – including one to a directory – is stored as a single symlink entry (`Path::is_dir()` would follow it and archive the target tree).
    - It discards the temp file without touching an existing archive when nothing was actually added, so a prior good backup is never replaced by an empty tarball.
- `update/` – every-invocation self-update. The release check itself is core's `release.rs` (per-release-line, daily-cached, ETag; see the core [CLAUDE.md](../ss-magic-core/CLAUDE.md)), imported here as `ss_magic_core::release`. The CLI uses its `CLI_LINE` (`v` tags) and the cache-free `resolve_newest_uncached` behind `ss-magic update`; `UreqReleaseClient::new` is the CLI's `ss-magic/<version>` shorthand. The `Cache` record is additive (new fields skip-if-`None`), so the CLI's `version-check.json` stays byte-compatible with older binaries.
  - `update/mod.rs`'s `update_command_with` decides in a fixed order before any download: no tag resolved → `UpdateReport::Unavailable` ("could not check", deliberately distinct from "already latest"; the backend is never constructed); a tag failing the CLI filter → `Unavailable`; not newer → `AlreadyLatest`; else the swap.
  - `update/apply.rs` does the fd-lock / download / atomic swap / spawn-and-wait re-exec via the `self_update` crate. EVERY entry point (`apply_update`, `apply_update_unlocked`, `run_self_update`) takes a mandatory `&str` tag: `target_version_tag` is always pinned, so the backend can never pick "latest" itself and install a plugin release over the CLI. A compile-time test pins the signatures.
  - Integrity rests on TLS + cargo-dist checksums (no SHA-256-vs-asset-digest check; the conformance notes are in the module docs of `update/apply.rs`). `bin_path_in_archive` matches cargo-dist's `<bin>-<target>/` tarball layout, and a test pins `BIN_NAME == CARGO_PKG_NAME` because that name is the `<bin>` half.
- `assets/magic.sh` – the canonical wrapper script, embedded into the binary via `include_str!`. Migration and init write that body to `.superset/magic.sh`. Edit `assets/magic.sh` and re-run migration/init to propagate. The binary is the sole file-copy implementation.
- `saphyr` (YAML 1.2, default features off) is a dependency of this crate ONLY, used solely by `orca/orca_yaml.rs` to locate and re-check the two managed keys of `orca.yaml`. It must never be added to core or the plugin crate (`--check`'s `workspace shape` assertion and CI's `cargo tree -i` loop both refuse it), and it must never SERIALIZE `orca.yaml`: the file is edited as text so the person's comments survive. It requires `thiserror` 2.0.20 or newer.
