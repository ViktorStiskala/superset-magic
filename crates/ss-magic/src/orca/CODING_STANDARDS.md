# Coding standards: Orca compatibility (`crates/ss-magic/src/orca/`)

The rules the CLI's Orca code follows – generating `orca.yaml` and `.worktreeinclude` from `magic.json`, detecting an Orca worktree, and the skip set forward sync uses there – on top of the repository-wide [CODING_STANDARDS.md](../../../../CODING_STANDARDS.md).

The Orca files are a leak and side-effect surface of their own: `.worktreeinclude` tells ANOTHER program which files to copy, and the end-of-sync refresh WRITES INTO THE SHARED MAIN CHECKOUT from a background setup script. Most rules below are the form the repository's secret-safety rules (positive determination, fail closed, filter at the point of final enumeration) take here. Module-level behavior is described in [CLAUDE.md](./CLAUDE.md).

## Ownership and source of truth

- **`magic.json` is the only source of truth.** Both Orca files are GENERATED from `magic.json`; nothing reads a setting FROM `orca.yaml` or `.worktreeinclude` into `magic.json`, which would make either a second source of truth. Reading them for what Orca will do is fine and expected – the refresh reads `orca.yaml`'s shared list to drop files under shared directories, and forward sync reads main's `.worktreeinclude` as its skip set. Orca logic lives in this module; core holds only the generic plumbing it calls, and the plugin crate has no Orca code at all (that `saphyr`, the YAML parser, stays out of core and the plugin is checked by `--check` and `cargo tree -i`).
- **Lines ss-magic did not write survive.** In `.worktreeinclude` ss-magic owns the marked section only; in `orca.yaml`, two keys (`scripts.setup` is ensured, `worktree.sharedDirectories` is owned and replaced). Every other line, key and comment is the person's and must survive each rewrite. A begin marker with no end marker does not extend the section to the end of the file – only the stray marker is dropped.
- **Never rebuild an unreadable file from an empty parse.** An existing file that cannot be read as UTF-8 text is never rewritten by any path, because rebuilding it from nothing drops the person's lines. "Absent" and "unreadable" are different answers and must stay distinguishable.

## The snapshot (`.worktreeinclude` entries)

- **A file enters the snapshot only on git's POSITIVE word.** "Ignored and untracked" is answered by one bulk `git::ignored_untracked` call over the whole candidate list. A git failure, a non-git root or an unanswerable path means the file is NOT listed – leaving a file out is always safe, because forward sync still copies whatever the snapshot omits. Never derive "ignored" by absence from a tracked set, never treat a git error as "ignored", never replace the bulk probe with per-path calls, and never add `--no-index` (it would report tracked files).
- **The snapshot never lists a directory, and its walk prunes in place.** A matched directory is expanded to its files with the excluded trees, the `DEFAULT_EXCLUDES` names and any directory holding a `.git` entry pruned IN THAT WALK, so a bare `.superset` or a broad `**` can never list a recovered secret or a dependency tree. Filtering only the flat match list is not enough; see [pack-backups-exclusion-must-guard-the-directory-walk.md](../../../../docs/solutions/logic-errors/pack-backups-exclusion-must-guard-the-directory-walk.md).
- **The snapshot is "what forward sync would copy", through the same matcher.** Patterns are expanded with `apply::match_paths`, never a second expansion. A symlink that is itself a match and points at a regular file is a candidate (forward sync and Orca's copier both copy its target); a link to a directory, a dangling link and a link met while walking a matched directory are not, because forward sync does not copy those either. The snapshot's definition follows forward sync in both directions – neither narrower nor wider.
- **Drop what would break or fool the probe before asking git.** Anything beneath a symlinked directory or inside a `.git`-holding directory is dropped first, because git aborts the whole batch on such a pathspec. A path Orca would misread (`worktreeinclude::is_listable`) is never listed.
- **Count the person's lines before capping.** The snapshot is capped at what is left of Orca's entry and byte budget AFTER the hand-written lines are counted, and files under a directory that made the shared list are dropped first.

## Shared directories

- **Detection walks by name over a fixed list of kinds, and a pattern only selects.** The walk records the known dependency-directory kinds only, never descends into a directory it recorded, follows no symlink, and stays out of the excluded trees and any `.git`-holding directory. Stored globs are matched AGAINST those candidates: a pattern narrows the detected kinds and can never make a directory of another kind shareable or stop the walk at a non-kind directory (a pattern matching a tracked parent once hid the `node_modules` beneath it).
- **Only directories git positively reports as ignored and untracked are shared.** A tracked or unignored directory, including an ignored one that holds a tracked file, is never shared.
- **Nobody asked means nobody chose "none".** With nothing stored and nothing detected, a non-interactive path (scripted init, migrate) leaves the `sharedDirectories` key ABSENT; writing `[]` would record "chose none" on nobody's behalf and freeze that for every later run. A stored list, an empty one included, is kept as it is, and only the interactive picker's answer is stored unconditionally. `sharedDirectories` is read from the base `magic.json` only, never from the per-machine overlay.

## `orca.yaml` editing

- **Edit as text; the re-parse is the arbiter.** `orca.yaml` is never re-serialized (no crate round-trips YAML with its comments). New text is spliced in at the located offsets and the result is parsed again; it is written only when it is one YAML 1.2 document whose two managed values are the intended ones and whose every other key, at the top level and beside the managed keys, has the same value in the same order. Never write a result the re-parse check did not confirm, and never weaken the comparison of unmanaged keys. A wrong position guess can then only ever produce a refusal.
- **The refusal ladder describes the FILE, not the edit.** It runs on every write, even when both managed values are already right, and for both managed parents on a refresh that does not edit the setup script. Only the `%YAML 1.1` directive refuses (the one version whose rules Orca's parser would switch to); do not widen it to "anything but 1.2".
- **An anchor or tag on a managed node is not a refusal by itself.** It stays in place and the edit goes ahead; the re-parse check refuses when another key referring to the anchor changes with it. Do not strip it and do not refuse it outright.
- **A refusal leaves the file byte-for-byte untouched and is never a failed command.** The reason and the block to add by hand are printed, and everything else the operation writes is still written. A missing parent key is never a refusal – a block is appended.
- **Preserve the file's own form.** Line endings follow the file and a leading BOM is preserved. `saphyr`'s span ends are not trustworthy for every node kind, so the editor scans for those ends itself; do not simplify that into trusting the spans.
- **`scripts.setup` is ensured, never duplicated or rewritten.** The setup line is prepended only when no trimmed line of the script already equals it (its equality with the migrate wrapper entry is pinned by a test).
- **Neither refresh touches the `scripts.setup` of an existing `orca.yaml`.** The explicit refresh writes the setup line only into a file it creates; the automatic refresh never touches `orca.yaml` at all. A line someone removed comes back only through init, migrate or edit-config. A refresh also never stores detected patterns into `magic.json` on its own.

## Writing across the finishing prompt (init, migrate, edit-config, `ss-magic orca`)

- **Compute before the prompt, write after the tree; never recompute at apply.** The whole Orca output, snapshot included, is planned before the finishing prompt so the "This will:" list describes it, and `apply` writes exactly what was planned after `.superset` materializes. Recomputing inside `apply` makes the written file differ from what the person confirmed; a file the same operation creates afterwards joins with the next refresh instead. Do not move the computation to after the prompt to "fix" drift either – the summary must describe the plan.
- **A planned write lands only on the file it was planned from.** Each planned write keeps its baseline (the exact text read, or "absent") and is re-read and compared on exact bytes right before the write. Other bytes, a file where there was none, no file where there was one, or a file that cannot be read again all leave it byte-for-byte untouched with a warning naming the command that updates it – never overwritten with the planned text and never silently re-planned. An unreadable re-read counts as changed. The other planned writes still go ahead.
- **Never describe the window as closed.** The re-read only narrows the hazard to the instant between the re-read and the rename, and an edit landing there is still lost; a comment or doc calling the window closed is a defect.
- **`.worktreeinclude`'s ignore rule is one recorded answer.** This is the Orca form of the repository-wide "a prompt describes exactly the action that runs" rule: tracked, already gitignored or gains a rule is asked once at plan time and `apply` acts on the record, never asking git again. "Tracked" is positive determination, and every "git could not be asked" lands on the side that promises and adds the rule. A tracked `.worktreeinclude` gets no ignore rule (a rule cannot ignore a tracked file), and an "already gitignored" answer still re-ensures the rule, so one removed during the prompt is put back.
- **The explicit path writes through in-repo links and refuses ones that leave the repository.** Containment is checked before either file is read: a target resolving outside the repository through a symlink is left untouched and reported, an in-repo link is written through onto its target. Every layout-writing operation goes through the one `plan`/`apply` path, never an inline copy of the write sequence. (That a committing finishing action stages `orca.yaml` but never the per-machine `.worktreeinclude` is pinned by a test.)

## The automatic end-of-sync refresh

- **It writes only `.worktreeinclude`, and only when that name is not a symlink and git positively says it is untracked AND ignored.** It never touches `orca.yaml` (a tracked file must not show up modified in main), never rewrites a file it cannot read, runs only after a successful copy, and never changes the sync's exit status – every reason not to write is a skip reported as a warning. "Git could not be asked" is a no, and so is an entry that could not be inspected. "Tracked" is asked under every spelling of the name (`:(icase)`, the repository-wide rule), since a case-insensitive volume resolves `.worktreeinclude` to a file committed as `.WorktreeInclude`.
- **The link check comes first and never asks where the link leads.** Git answers for the NAME, so an untracked, ignored link to a tracked file passes both git questions while a write through it lands on the tracked target. The entry is inspected without following anything before git is asked and before the file is read, and any link – to a tracked file, an untracked one, a directory or nothing, inside the repository or out – is a skip. A file that does not exist yet is not a link and is created.
- **The refresh never follows a link at the target name, and the two write paths stay different.** It repeats the link inspection right before the write and writes only through `replace_refreshed` (core's `write_atomically_no_follow`); never route it through a following writer (`write_atomically`, `write_contained`, `fs::write`). Writing through a link that stays inside the repository belongs to the explicit path alone – do not make the explicit path no-follow, nor the refresh follow.

## Orca worktree detection and the forward-sync skip set

- **Orca mode needs a variable that NAMES this worktree, and is never on in the main checkout.** Detection compares canonicalized absolute paths from `ORCA_WORKTREE_PATH` or `ORCA_WORKTREE_ID`; the variables merely existing changes nothing, so an Orca terminal that changes into another repository behaves as a plain terminal does there. A relative value is never a match. The environment is an injected lookup, never read from the process inside detection.
- **Only forward sync behaves differently in an Orca worktree.** The Sync cockpit, `reverse-sync` and `pack` ignore Orca mode, and outside an Orca worktree forward sync behaves exactly as before. `--no-orca-skip` disables the skip, not the refresh.
- **The skip set is read once, before the copy, and holds listed paths that EXIST in the worktree.** It is read from main's `.worktreeinclude` right after `magic.json` loads, so a path the end-of-sync refresh adds – not in the list Orca used – is never skipped on its strength. Existence is checked without following a symlink; a listed directory that exists covers everything under it (the set holds the directory, not its expanded files), and a listed path that is absent is still synced. An unreadable list yields an empty set plus a warning.
- **The backup pass runs with the same filter as the copy.** A path the copy leaves to Orca is not overwritten, so backing it up would only store one more copy of a secret; a backup pass with a different filter is a defect.
- **The reader matches Orca's own parsing.** `.worktreeinclude` is read the way Orca reads it (trim, skip blank and `#` lines, normalize separators and one leading `./` and trailing `/`, reject globs, `!`, absolute paths, `..`, empty segments and `.git`), because that list decides what forward sync skips.

## Tests

- **An Orca test asserts the specific outcome of the rule it names.** A refusal test requires that rule's own reason, not "some refusal", which any other rule satisfies; a fixture is checked with git before the assertion so the guard is actually exercised (an ignored directory that holds a tracked file must really be ignored and the file really tracked).
